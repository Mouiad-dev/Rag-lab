# ADR-0001: Provider-agnostic model layer

Date: 2026-10-26
Status: accepted (library choice re-verified 2026-11-02; P2.2 uses a direct Ollama adapter, see Update 2026-11-02)

## Context
Users must be able to pick any LLM, embedding or reranking provider: paid APIs (Anthropic, OpenAI, Google, Mistral, Cohere and others), free or open-weight models, and local runtimes (Ollama, LM Studio, vLLM). Kimi models from Moonshot are also wanted. The request said "km3"; we assume this means the Kimi K-series served by Moonshot's OpenAI-compatible API or as open weights through vLLM/Ollama. Confirm the exact model. A public install must work with zero paid keys. The old plan tied model access to LangChain integrations.

## Decision
1. **Own ports** in `packages/providers`: `ChatModel`, `EmbeddingModel`, `Reranker`, each with sync/async calls, streaming for chat, structured output where supported, and a `Usage` record (provider, model, tokens in/out, latency, estimated cost).
2. **Registry and model profiles.** A profile = provider + model ID + base URL (optional) + capability flags: `tool_calling`, `structured_output`, `vision`, `streaming`, `context_window`, `max_output_tokens`, `embedding_dim`, `token_embeddings`, `multivector`, `local`, `cost_per_mtok_in`, `cost_per_mtok_out`. Flags are declared in config and verified by an opt-in probe.
3. **Per-pipeline choice.** Each stage (generator, embedder, reranker, query_transform, judge, chunk_llm, scout) references a profile ID. The resolver rejects a pipeline whose stage needs a capability its profile lacks, before a job starts.
4. **Configuration.** Secrets only from env vars (for example `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`); profiles from `config/providers.yaml` (example: `config/providers.example.json`) and later the settings UI, which shows key presence, never values.
5. **Default adapter: LiteLLM**, wrapped by our ports. Native SDK adapters (for example the Anthropic SDK) may implement the same ports when a feature (prompt caching, extended thinking, batch) is not exposed well enough.
6. **Defaults.** Local: Ollama chat + Ollama embeddings. Paid example: Anthropic. Rerankers: a local cross-encoder plugin plus API rerankers through the port.
7. **Embedding identity** = provider + model + revision + preprocessing + dimension; changing any of these creates a new index (see PROJECT_ARCH.md §9).

## Alternatives
- **LangChain chat-model integrations only.** Rich ecosystem and already used for LangGraph, but one package per provider, uneven feature parity, frequent API churn, and framework types leaking into domain code. Kept as a consumer of our ports (a thin LangChain wrapper around `ChatModel`) for LangGraph workflows.
- **LiteLLM as default (chosen).** One dependency covers 100+ providers including Ollama, any OpenAI-compatible server (LM Studio, vLLM, Moonshot), Anthropic, Gemini, Mistral; unified chat, embedding and rerank calls; a maintained model cost map; optional proxy mode for teams. Risks: a broad, fast-moving dependency surface and occasional lag on new provider features. Mitigation: pin exact versions with hashes, wrap behind ports, keep native adapters possible, run a provider contract suite.
- **Native SDK per provider only.** Maximum fidelity but the most code to maintain; used selectively.
- **OpenAI-compatible HTTP only.** Simple and covers many local servers, but not every provider's native features or embeddings/rerank APIs.

## Consequences
- Domain and technique code never imports a vendor SDK (rule in `.claude/rules/10-architecture.md`).
- Cost and usage are measured uniformly, enabling budgets for experiments and the Tech Scout.
- Contract tests run against a fake provider in CI; live tests are opt-in and skipped without keys.
- Capability flags can be wrong; the probe and explicit errors are the guard. Cost estimates are estimates, not invoices.

## Evidence
To verify at P2.1 against current official docs: LiteLLM provider list, embedding/rerank support, cost map, async/streaming APIs; Ollama and LM Studio OpenAI-compatible endpoints; Moonshot API compatibility.

## Update 2026-11-02 (P2.2)
P2.2 uses a direct Ollama HTTP adapter on httpx (optional extra `rag-foundry-providers[ollama]`, `httpx==0.28.1`) instead of LiteLLM. Reasons:
- User decision 2026-11-02, overriding the Evidence verdict "FITS" for P2.2. Malware shipped in litellm 1.82.7/1.82.8 (GHSA-5mg7-485q-xm76). Every release outside the GHSA-w4c7-34wj-hqm8 range (Enterprise proxy only) is under 2 weeks old, so none meets the pin rule today.

### Verified 2026-11-02 (P2.3-01), Anthropic Messages API
All access dates are 2026-11-02. 1. **Endpoint and headers.** `POST https://api.anthropic.com/v1/messages`. Required: `anthropic-version` (current value `2026-10-21`, the newest in the version history), `content-type: application/json`, and auth. The overview lists `Authorization: Bearer <key>` as the primary header and `x-api-key` as a "legacy fallback ... still supported". Optional `anthropic-workspace-id` (needed only for keys not scoped to one workspace). Sources: `D/api/overview`, `D/api/versioning`, `D/api/messages` (retrieved 2026-11-02).
2. **Request.** `max_tokens` is required (a number, minimum 0). `messages` roles are `user` and `assistant` only; the system prompt is the top-level `system` (string or text blocks). Consecutive same-role turns are combined into one turn. A final `assistant` message is prefill; Claude Haiku 5.5 rejects prefill with 400 even with thinking off. **`temperature`, `top_p`, `top_k` are removed in `anthropic-version: 2026-10-21`: sending any returns 400 on every model, even at the default.** Haiku 5.5 and Sonnet 5.5 also return 400 for them (their migration guides say to omit them; for Sonnet 5.5 "Setting `temperature`, `top_p`, or `top_k` returns a 400 error"). The port field `temperature` must therefore not be sent to these models. **Thinking is ON by default for both models (adaptive)**, so output tokens include hidden thinking and a small `max_tokens` can end with `stop_reason: max_tokens` and no text. Haiku 5.5 accepts `thinking: {"type": "disabled"}` at effort `high` or below (default effort `medium`). Sonnet 5.5 rejects `disabled` with 400; use `thinking: {"type": "between_tools"}` (accepted at effort `high` or below). Thinking tokens are billed even when `display` is `omitted`. Sources: `D/api/messages`, `D/api/migration-2026-10-21`, `D/models/haiku-5-5/migration-guide`, `D/models/sonnet-5-5/migration-guide`, `D/build-with-claude/thinking` (retrieved 2026-11-02).

The reference types `MessageDeltaUsage` with cumulative `input_tokens` (nullable), `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`; the docs example shows only `output_tokens`, so treat the others as optional. **Verdict: FITS with direct httpx.** All facts needed for 03..05 were confirmed from official pages. Two changes versus the planning assumptions: `temperature` must not be sent, and thinking is on by default, so the adapter and the live test must set `thinking` explicitly (Haiku: `disabled`).

**Decision for P2.3: direct httpx adapter** (`rag-foundry-providers[anthropic]` using the already locked `httpx==0.28.1`; send `anthropic-version: 2026-10-21`). Reasons: no new dependency (the SDK would add `httpx2`, `anyio`, `jiter`, `opentelemetry-api` and others); `token_source` stays `PROVIDER` because the adapter reads the raw `usage` object including cache fields; no hidden retries (the SDK retries twice by default) and no logging switch to police; same pattern as the P2.2 Ollama adapter. No P2.3-scope feature needs the SDK. LiteLLM is not recommended: no pin is both 2 weeks old and outside every advisory range until 2026-11-11, it has a large dependency surface, and it would hide the raw usage fields.

**Live-run cost estimate (05), Haiku tier, about 8 calls, at most 64 output tokens and about 30 input tokens each.**
- Formula: cost = calls * (in_tokens * 0.10 + out_tokens * 0.50) / 1,000,000 = 8 * (30 * 0.10 + 64 * 0.50) / 1e6 = 8 * 35 / 1e6 = USD 0.000280 (input 0.000024 plus output 0.000256).
- Upper bound with `inference_geo: "us"` (1.1x): USD 0.000308.
- Thinking tokens count inside `max_tokens` and are billed as output, so the 64-token cap still bounds the cost. Send `thinking: {"type":"disabled"}` or the reply may contain no text.
- For reference, the same load on `claude-sonnet-5-5` is 8 * (30 * 2 + 64 * 10) / 1e6 = USD 0.005600.
- The newer tokenizer makes "about 30 input tokens" approximate; this is an estimate, not an invoice.

**Open points for 03..05 (not blockers).** (1) The version header is set to `2026-10-21`. The docs still describe `2023-06-01` as the previous version, but I found no sunset date for it (not confirmed). (2) The adapter must drop or reject the port's `temperature` field for these models. (3) Streaming `message_delta` `input_tokens` is nullable; take input counts from `message_start` and cumulative values from the last `message_delta`. (4) `Authorization: Bearer` and `x-api-key` are both documented; the spec names `x-api-key`, which the docs call "still supported".

**Owner decisions 2026-11-02 for 03..05.** Send `Authorization: Bearer <key>` (primary per the API overview; no `x-api-key`) and `anthropic-version: 2026-10-21`. A request that sets `temperature` is refused with a typed error, never silently dropped. Thinking is set explicitly: Haiku 5.5 profiles send `thinking: {"type": "disabled"}` (effort, if ever set, goes in `output_config.effort`); Sonnet 5.5 cannot disable thinking, so its default `max_tokens` leaves room for billed thinking tokens. Streaming takes input counts from `message_start` and cumulative counts from the last `message_delta`.

All access dates are 2026-11-02. Every source is an official page fetched with a plain HTTP GET, or the official PyPI and GitHub APIs. Nothing was installed, no API call was made, no key was used. Short names for URL bases: `OA/` = `https://developers.openai.com/api/` (the `.md` rendering of each page; `platform.openai.com/docs/api-reference/...` returned HTTP 403 to curl, and `developers.openai.com` is the same OpenAI reference), `LM/` = `https://lmstudio.ai/docs/`, `VL/` = `https://docs.vllm.ai/en/latest/`, `KM/` = `https://platform.kimi.ai/docs/` (Moonshot's official platform docs; the docs host `platform.moonshot.ai` redirected to `platform.kimi.ai`, and the API host is `api.moonshot.ai`). "not confirmed" means no official page fetched today states it.

**1. Chat Completions (OpenAI reference, `OA/reference/resources/chat/subresources/completions/methods/create.md`).**
- Endpoint `POST /v1/chat/completions`; auth `Authorization: Bearer <key>` (`OA/reference/overview.md` and the examples on the same pages). Request fields we send: `model`, `messages`, `temperature` (number 0 to 2, default 1), `stream`, `stream_options.include_usage`, and a token cap.
- Message roles in the reference: `developer`, `system`, `user`, `assistant`, `tool`, plus deprecated `function`. Our port roles (`system`, `user`, `assistant`, `tool`) are all in this list.
- Token cap: `max_tokens` is "now deprecated in favor of `max_completion_tokens`, and is not compatible with o-series models"; `max_completion_tokens` includes visible output and reasoning tokens. LM Studio documents `max_tokens` (see 4). The adapter must therefore make the field name a per-profile setting (`max_tokens` for local servers; `max_completion_tokens` for OpenAI and Moonshot).
- Response: `choices[].message.content`; `finish_reason` is one of `stop`, `length`, `tool_calls`, `content_filter`, `function_call` (deprecated). `usage`: `prompt_tokens`, `completion_tokens`, `total_tokens`, `completion_tokens_details.reasoning_tokens` and others, `prompt_tokens_details.cached_tokens` (default 0), `cache_write_tokens`, `audio_tokens`, `image_tokens`. The reference does not state whether `prompt_tokens` includes `cached_tokens` (the Moonshot page below states it does); for OpenAI this is not confirmed.
- Streaming SSE: lines are `data: {chunk json}`, terminated by `data: [DONE]` (example in the same page). `stream_options.include_usage` (boolean): "an additional chunk will be streamed before the `data: [DONE]` message. The `usage` field on this chunk shows the token usage statistics for the entire request, and the `choices` field will always be an empty array. All other chunks will also include a `usage` field, but with a null value." and "If the stream is interrupted, you may not receive the final usage chunk." Also `stream_options.include_obfuscation` (adds an `obfuscation` field to deltas; may be set false).
- Error shape mid-stream: not confirmed. The chat reference shows no error event; the OpenAPI spec (https://raw.githubusercontent.com/openai/openai-openapi/manual_spec/openapi.yaml, `info.version` 2.3.0) defines an `ErrorEvent` ("Occurs when an error occurs ... internal server error or a timeout") for other streaming APIs, not for chat. The adapter should treat a stream that ends without `[DONE]`, or a data line with a top-level `error` key, as a typed error (a defensive choice, not a documented contract).

**2. Embeddings (`OA/reference/resources/embeddings/methods/create.md`).** `POST /v1/embeddings`. Request: `input` (string, array of strings, array of token ids, or array of arrays; arrays have 1 to 2048 items; max 8192 tokens per input; no empty string), `model` (`text-embedding-ada-002`, `text-embedding-3-small`, `text-embedding-3-large` or any string), optional `dimensions` (text-embedding-3 and later only), `encoding_format` (`float` default or `base64`), `user`. Response: `data[]` of `{object: "embedding", index, embedding}` (`index` is "the index of the embedding in the list of embeddings", so the adapter sorts by `index`), `model`, `object: "list"`, `usage: {prompt_tokens, total_tokens}`. We send `encoding_format: "float"` and a list `input`.

**3. Errors and request id.** Body (OpenAPI spec `components.schemas.ErrorResponse` and `Error`, URL above): `{"error": {"code": string|null, "message": string, "param": string|null, "type": string}}`. Documented statuses (`OA/docs/guides/error-codes.md`): 400, 401 (invalid authentication, incorrect API key, not in an organization, IP not authorized), 403 (country or region not supported), 429 (rate limit, credit balance exhausted, spend or usage limits, "slow down"; billing causes are told apart by `error.code`, while `error.type` can still be `insufficient_quota`), 500, 503 (model overloaded). The page says the Python SDK raises `RateLimitError` for 429 and `InternalServerError` for 503, so retry classification should look at the body, not the status alone. Request id header: `x-request-id` ("Unique identifier for this API request"; `OA/reference/overview.md`). Auth header: `Authorization: Bearer <key>`.

**5. Moonshot (Kimi).** All from `KM/` pages.
- Base URL: `https://api.moonshot.ai/v1` (`KM/guide/kimi-k3-quickstart.md`, `KM/api/chat.md`); chat path `POST /v1/chat/completions`; auth `Authorization: Bearer $MOONSHOT_API_KEY`. A China-region endpoint is not confirmed: the errors page (`KM/api/errors.md`) only says keys from `platform.kimi.ai` are independent of keys from "other regional Kimi platforms" and that mixing returns 401. We use `https://api.moonshot.ai/v1` only.
- Model IDs, verbatim (`KM/models.md`, `KM/pricing/chat.md`): `kimi-k3.1-pro`, `kimi-k3.1-pro-highspeed`, `kimi-k3`, `kimi-k2.7-code`, `kimi-k2.7-code-highspeed`, `kimi-k2.6`. Discontinued: `kimi-k2.5` and `moonshot-v1-*` (2026-08-31), `kimi-k2` series (2026-05-25). K2 models close to new users from 2026-10-31 and are to be retired by end of December 2026. The ADR "km3" assumption: not confirmed as an exact string; there is no model called `km3`, and the closest official ID is `kimi-k3` (previous-generation flagship; `kimi-k3.1-pro` is the newest). The owner picks.
- Context window: 1,048,576 tokens for the K3 series; 262,144 for the K2 series (`KM/pricing/chat.md`).
- K3 behaviour that affects the adapter (`KM/api/models-overview.md`, `KM/guide/kimi-k3-quickstart.md`): thinking is always on; top-level `reasoning_effort` is `low`, `high` or `max` (default `max`); `temperature` is fixed at 1.0, `top_p` 0.95, `n` 1, penalties 0, and "passing any other value returns an error, so do not pass it explicitly" (same rule as P2.3: do not send `temperature`). `max_tokens` is deprecated in favour of `max_completion_tokens` (default 131072, up to 1048576; it is the output length, not input plus output). Reasoning arrives in `reasoning_content`, the answer in `content`; `finish_reason` is `length`, `stop` or `tool_calls`.
- Streaming: `stream: true` with `stream_options.include_usage: true`; the final usage chunk has `choices: []` and top-level `usage`; the stream ends with `data: [DONE]` (`KM/api/chat.md`, `KM/guide/utilize-the-streaming-output-feature-of-kimi-api.md`). Usage: `prompt_tokens` is "always the total number of input tokens"; `completion_tokens` includes `completion_tokens_details.reasoning_tokens` (example: 112 total, 90 reasoning); `prompt_tokens_details.cached_tokens` is cache read and `prompt_tokens_details.cache_write_tokens` is cache write; the three input parts are mutually exclusive and sum to `prompt_tokens`, so uncached input = `prompt_tokens - cached_tokens - cache_write_tokens`.
- Tool calling: yes (`tools`; `tool_choice` `auto`, `none`, `required` for `kimi-k3`). JSON mode: yes, `response_format` `{"type":"json_object"}` and `{"type":"json_schema", ...}` (`KM/api/chat.md`). Both stay declared `False` in P2.4.
- Errors: body `{"error": {"type": "...", "message": "..."}}`; statuses 400 (`content_filter`, `invalid_request_error`), 401 (`invalid_authentication_error`, `incorrect_api_key_error`), 403, 404 (`resource_not_found_error`), 429 (`engine_overloaded_error`, `exceeded_current_quota_error`, `rate_limit_reached_error`; honour `Retry-After`), 499, 500, 503, 504 (gateway timeout after 900 s with an HTML body, not JSON). A request-id response header name: not confirmed (the errors page mentions a `request_id` for support only). Rate-limit headers `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` are documented for web-search 429s; for chat: not confirmed.
- Embeddings: no Moonshot embeddings endpoint is listed in the official docs index (`KM/llms.txt`; no entry contains "embed"). Verdict: not confirmed to exist; treat as unavailable, and a Moonshot embedding profile fails explicitly.
- Prices, USD per MTok, flat (no tiering by context length), from `KM/pricing/chat.md`. The table is rendered client-side, so the values were read from the page's own data payload in the HTML GET; the `.md` rendering has an empty table.

  | `kimi-k3.1-pro` | 2.00 | 10.00 | 0.20 | 2.00 | 4.00 |

**Verdict: FITS with direct httpx, with gaps.** The OpenAI Chat Completions and Embeddings contracts are confirmed from the official reference. Moonshot documents the same chat contract (streaming with `include_usage`, `[DONE]`, usage and cache fields, error body). Not confirmed: LM Studio and vLLM stream usage and `[DONE]`, the mid-stream error shape, a Moonshot request-id header, a China endpoint, a Moonshot embeddings endpoint. These are handled by tolerant parsing and explicit failure, not by guessing, and are not blockers for the offline adapter (03..05).

**Decision for P2.4: one direct httpx `openai_compatible` adapter** (chat and embeddings) on the locked `httpx==0.28.1`, no new package. Facts that shape it: (a) endpoint, body and auth are the same across OpenAI, LM Studio, vLLM and Moonshot; (b) `token_source` is `PROVIDER` when the response carries `usage` (including streaming with `include_usage`), otherwise estimated or absent, never invented; (c) the token-cap field name (`max_tokens` or `max_completion_tokens`), whether `temperature` may be sent (not for Moonshot K3; refuse, do not drop), and whether cached tokens are inside `prompt_tokens` are per-profile settings; (d) the API key is optional for LM Studio and vLLM and required for OpenAI and Moonshot, read from an env var named in the profile, with `Authorization: Bearer` sent only when a key exists; (e) tools, structured output and vision are declared `False` and refused, although all four servers support tools in some form; (f) a stream is read as `data:` lines until `[DONE]`, and EOF without `[DONE]` is an error; (g) embeddings are sorted by `index`. LiteLLM is not recommended and no user stop is needed.

**Live-test cost estimate (possible later opt-in Moonshot test; about 6 calls, at most 64 output tokens and about 30 input tokens each).**
- Formula: cost = calls * (in_tokens * rate_in + out_tokens * rate_out) / 1,000,000, rates in USD per MTok.
- `kimi-k3`: 6 * (30 * 3.00 + 64 * 15.00) / 1e6 = 6 * 1,050 / 1e6 = USD 0.006300 (input 0.000540, output 0.005760).
- `kimi-k3.1-pro`: 6 * (30 * 2.00 + 64 * 10.00) / 1e6 = 6 * 700 / 1e6 = USD 0.004200.
- Caveats: K3 always thinks (default `reasoning_effort` `max`), so a 64-token `max_completion_tokens` may end with `finish_reason: "length"` and empty `content`; a test should set `reasoning_effort: "low"` and still expect that it may be cut off (the usage example shows `completion_tokens` including `reasoning_tokens`, so the cap probably covers both, but this is not stated outright). The USD 1 minimum top-up is far larger than the test cost. Estimate only, not an invoice. No live test is part of P2.4 done.

The K3 prices above are now confirmed and may be filled in the example file; any other price stays `null`. (2) LM Studio and vLLM stream usage is not confirmed; the adapter marks usage estimated or absent when a server omits it, and each server's opt-in live test must check it. (3) OpenAI `prompt_tokens` versus `cached_tokens` semantics are not confirmed. (4) Retry policy for 429 and 503 and the Moonshot 900 s gateway timeout belong to P2.5.

## Update 2026-11-03 (P2.4)
- Config format is JSON (`config/providers.json`), not YAML; it is validated by `rag_foundry_providers.config`. Stages are the closed set of seven roles.
- OpenAI-compatible endpoints (LM Studio, vLLM, Moonshot, OpenAI) use one direct httpx adapter; no new package.
- Tool-calling success paths move to P8.3 and structured output to the first step that needs it (P4.4 or P5.4); until then profiles cannot declare these flags `True` and adapters refuse them.
- Per-stage selection: `resolve_pipeline` rejects missing capability, wrong kind or unbound stage before any adapter is built or key read; `build_registry` binds adapters only for the stages in use.
- LiteLLM: still not used and not recommended (supply-chain incident, size, token-source honesty; see the P2.2 update). No stop needed.
- Owner decision 2026-11-03: paid (non-local) OpenAI-compatible endpoints default to an output cap of 4096 tokens when a request gives none; config rejects a non-local `openai_compatible` endpoint without `default_max_tokens`. Endpoint settings `max_tokens_field`, `supports_temperature` (default false on non-local) and `default_max_tokens` live on the endpoint in the config, passed through by `build_registry`.

## Update 2026-11-04 (P2.5)
- **Ownership.** Retries and per-call deadlines live only in provider-side wrappers in `packages/providers` (`resilience.py`), wrapping the bound adapter. Adapters keep doing one HTTP attempt each; domain and technique code never retries model calls. Budgets are hard caps checked before every attempt (`budget.py`). Wrapper order: `Resilient( Budgeted( Recording( adapter ) ) )`, so every attempt is budget-checked and recorded, and a budget error is never retried.
- **D1 attempts** (decided by owner 2026-11-04): `max_attempts = 3` (1 call + 2 retries).
- **D2 backoff** (decided by owner 2026-11-04): with no `Retry-After`, wait a uniform random 20-30 s. If `Retry-After` (delta-seconds) is <= 60 s, wait max(`Retry-After`, uniform 20-30 s). If it is > 60 s, fail at once with the original error. Sleep and random source are injected; tests never wait. (Replaces the planner's proposal of full jitter, base 0.5 s, cap 8 s.)
- **D3 retried errors** (decided by owner 2026-11-04): only `connection`, `rate_limited`, `overloaded`, `server_error` (500/502/503). `timeout` is retried only for `local` profiles. Every other error (`auth`, `billing`, `invalid_request`, `input_too_long`, `model_not_found`, `refused`, `bad_response`, budget errors, others) is raised at once, never swallowed. After the last attempt the last real typed error is raised. A stream is retried only if it failed before its first chunk.
- **D4 per-attempt deadline** (decided by owner 2026-11-04): 300 s for `complete`, `stream` (whole stream) and `embed`. Adapter httpx timeouts stay. Sonnet at 16384 output tokens may approach 300 s.
- **D5 per-run budget** (decided by owner 2026-11-04): no default amount. A run that binds any non-local profile must pass an explicit `RunBudget(max_usd=...)`, else `BudgetRequiredError`.
- **D6 local profiles** (decided by owner 2026-11-04): never blocked by the USD cap; they count toward `max_calls` only.
- **D7 unknown prices** (decided by owner 2026-11-04): a non-local profile without input or output price is refused before the call (`UnboundedCostError`). A finished call whose cost is None keeps its full reservation as spent. A `ProviderCallError` that carries a non-2xx HTTP `status` and no `usage` (an error reply that was not billed, for example a 503) settles to 0 USD; a 2xx reply that fails to parse may have been billed and keeps the full worst case; the call still counts toward `max_calls`. Connection errors, timeouts and cancellation (no reply) keep the full worst case as spent. A request-validation error raised before any I/O (for example `UnsupportedRequestError`, `MissingCapabilityError`) releases both the reservation and the call slot.
- **D8 stream stopped early** (decided by owner 2026-11-04): the full worst-case reservation stays counted as spent; the ledger records nothing (no invented usage). The same holds for a stream that fails after its first chunk without usage. A stream that fails before any chunk with an HTTP status and no usage follows the D7 rule (0 USD).
- **D9 worst-case cost per attempt** (decided by owner 2026-11-04, as proposed): input bound = UTF-8 bytes of all message contents, tool specs and response schema (JSON, `ensure_ascii=False`) + 64; output bound = `request.max_output_tokens` or the adapter default cap; input priced at max(input rate, cache-write rate when set). Embeddings: input only. Caveat: whether Moonshot K3 reasoning tokens fall inside `max_completion_tokens` is not confirmed.
- **D10 live evidence** (decided by owner 2026-11-04): Ollama (free) and Anthropic Haiku with a USD 0.05 cap, both approved. Moonshot, LM Studio and vLLM are not run.
- **429 classification.** OpenAI `insufficient_quota` (code or type) and Moonshot `exceeded_current_quota_error` map to `billing`; Moonshot `engine_overloaded_error` maps to `overloaded`. Anthropic spend-cap 429s have no `retry-after`; they fail after D1 attempts. Each such attempt is a reply with an HTTP status and no usage, so under D7 it is counted as 0 USD (the provider does not bill it); the attempts still count toward `max_calls`.
- **Rerankers.** `build_registry` binds rerankers unwrapped (fake only today), so a non-local reranker profile raises `ProviderUnavailableError` until P5.5 adds budgeted wrappers; nothing paid bypasses the budget.
