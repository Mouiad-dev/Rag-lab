# ADR-0001: Provider-agnostic model layer

Date: 2026-10-26
Status: accepted (library choice re-verified 2026-11-02; P2.2 uses a direct Ollama adapter, see Update 2026-11-02)

## Context
Users must be able to pick any LLM, embedding or reranking provider: paid APIs (Anthropic, OpenAI, Google, Mistral, Cohere and others), free or open-weight models, and local runtimes (Ollama, LM Studio, vLLM). Kimi models from Moonshot are also wanted. The request said "km3"; we assume this means the Kimi K-series served by Moonshot's OpenAI-compatible API or as open weights through vLLM/Ollama. Confirm the exact model. A public install must work with zero paid keys. The old plan tied model access to LangChain integrations.

## Decision
1. **Own ports** in `packages/providers`: `ChatModel`, `EmbeddingModel`, `Reranker`, each with sync/async calls, streaming for chat, structured output where supported, and a `Usage` record (provider, model, tokens in/out, latency, estimated cost).
2. **Registry and model profiles.** A profile = provider + model ID + base URL (optional) + capability flags: `tool_calling`, `structured_output`, `vision`, `streaming`, `context_window`, `max_output_tokens`, `embedding_dim`, `token_embeddings`, `multivector`, `local`, `cost_per_mtok_in`, `cost_per_mtok_out`. Flags are declared in config and verified by an opt-in probe.
3. **Per-pipeline choice.** Each stage (generator, embedder, reranker, query_transform, judge, chunk_llm, scout) references a profile ID. The resolver rejects a pipeline whose stage needs a capability its profile lacks, before a job starts.
4. **Configuration.** Secrets only from env vars (for example `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`); profiles from `config/providers.yaml` (example: `config/providers.example.json`) and later the settings UI, which shows key presence, never values.
5. **Default adapter: LiteLLM**, wrapped by our ports. Native SDK adapters (for example the Anthropic SDK) may implement the same ports when a feature (prompt caching, extended thinking, batch) is not exposed well enough.
6. **Defaults.** Local: Ollama chat + Ollama embeddings. Paid example: Anthropic. Rerankers: a local cross-encoder plugin plus API rerankers through the port.
7. **Embedding identity** = provider + model + revision + preprocessing + dimension; changing any of these creates a new index (see PROJECT_ARCH.md §9).

## Alternatives
- **LangChain chat-model integrations only.** Rich ecosystem and already used for LangGraph, but one package per provider, uneven feature parity, frequent API churn, and framework types leaking into domain code. Kept as a consumer of our ports (a thin LangChain wrapper around `ChatModel`) for LangGraph workflows.
- **LiteLLM as default (chosen).** One dependency covers 100+ providers including Ollama, any OpenAI-compatible server (LM Studio, vLLM, Moonshot), Anthropic, Gemini, Mistral; unified chat, embedding and rerank calls; a maintained model cost map; optional proxy mode for teams. Risks: a broad, fast-moving dependency surface and occasional lag on new provider features. Mitigation: pin exact versions with hashes, wrap behind ports, keep native adapters possible, run a provider contract suite.
- **Native SDK per provider only.** Maximum fidelity but the most code to maintain; used selectively.
- **OpenAI-compatible HTTP only.** Simple and covers many local servers, but not every provider's native features or embeddings/rerank APIs.

## Consequences
- Domain and technique code never imports a vendor SDK (rule in `.claude/rules/10-architecture.md`).
- Cost and usage are measured uniformly, enabling budgets for experiments and the Tech Scout.
- Contract tests run against a fake provider in CI; live tests are opt-in and skipped without keys.
- Capability flags can be wrong; the probe and explicit errors are the guard. Cost estimates are estimates, not invoices.

## Evidence
To verify at P2.1 against current official docs: LiteLLM provider list, embedding/rerank support, cost map, async/streaming APIs; Ollama and LM Studio OpenAI-compatible endpoints; Moonshot API compatibility.

### Verified 2026-11-02 (P2.2-01), Ollama chat and embeddings only
All access dates are 2026-11-02. Facts come from the official PyPI JSON API, the BerriAI GitHub repository (API and raw source at tag `v1.106.6`), docs.litellm.ai and the Ollama docs. Nothing was installed or pulled. Source-code facts are read from the tag, not run; they are not live-tested.

Affected range `>=1.82.7,<=1.82.8`. Source: https://github.com/advisories/GHSA-5mg7-485q-xm76

The newest, GHSA-w4c7-34wj-hqm8 (critical, 2026-10-27), says it affects a proxy running with an Enterprise license (unauthenticated file read) and that open-source deployments without a license are not affected. Its fixed versions are `1.103.10`, `1.104.8`, `1.105.6` and `1.106.5`; affected is `<1.106.5` on the 1.106 line. Embeddings: `ollama/<model>` (the `aembedding` dispatch branch is keyed on provider `ollama`; it calls `/api/embed`). `api_base` is passed as a keyword argument, else `OLLAMA_API_BASE`, else `http://localhost:11434`. `acompletion`, `acompletion(stream=True)` (docs page "Streaming + Acompletion") and `aembedding` exist. Sources: https://docs.litellm.ai/docs/providers/ollama , `litellm/main.py` and `litellm/llms/ollama/` at tag v1.106.6: https://github.com/BerriAI/litellm/blob/v1.106.6/litellm/main.py
4. **Usage and `token_source`.**
   - Chat, non-streaming: `usage` uses Ollama's `prompt_eval_count` and `eval_count` when present and otherwise falls back to `litellm.token_counter` (LiteLLM's own tokenizer). Chat, streaming: usage is attached to the final `done` chunk only when both counts are integers; otherwise there is no usage. Embeddings: `prompt_eval_count` from `/api/embed` when present, else an estimate via the tokenizer, else `0` with a warning. Sources: `litellm/llms/ollama/chat/transformation.py`, `litellm/llms/ollama/completion/handler.py` at v1.106.6.
   - The returned `usage` object does not say whether a count was reported or computed. The adapter cannot tell them apart from the LiteLLM response in the non-streaming chat and embedding paths. Consequence for `token_source`: label `PROVIDER` only when the adapter itself sees the raw counts, otherwise `ESTIMATED`. P2.2-03/04 must decide how to see the raw counts (for example a custom `logging_obj` hook or a raw `/api/embed` read); this is an open design point, not resolved here. Ollama documents `prompt_eval_count` and `eval_count` on chat responses and `prompt_eval_count` on `/api/embed`: https://github.com/ollama/ollama/blob/v0.40.13/docs/api.md
5. **Retries and timeouts.** `litellm.num_retries` defaults to `None` (no LiteLLM-level retry loop); pass `num_retries=0` per call to be explicit. `DEFAULT_MAX_RETRIES` is 2 but is not applied to the Ollama path in the code read. Default request timeout is the `request_timeout` setting, which chat `completion()` maps to 600 s when the caller sets none; pass `timeout=` per call. The Ollama embedding handler does not forward a per-call `timeout` (it posts through the module-level HTTP client), so P2.5 must enforce embedding timeouts around the call (for example `asyncio.timeout`). Sources: `litellm/__init__.py`, `litellm/constants.py`, `litellm/main.py`, `litellm/llms/ollama/completion/handler.py` at v1.106.6; https://docs.litellm.ai/docs/completion/reliable_completions

Set `LITELLM_LOCAL_MODEL_COST_MAP=True` before import to use the bundled map with no fetch. Also, when `LITELLM_MODE` is unset (default `DEV`), import runs `dotenv.load_dotenv()`; set `LITELLM_MODE=PRODUCTION` to stop that. No SDK telemetry setting or call was found in `__init__.py`, `main.py`, `utils.py` or `constants.py` at v1.106.6 (grep of those files only; absence in the whole package is not confirmed). Sources: https://github.com/BerriAI/litellm/blob/v1.106.6/litellm/litellm_core_utils/get_model_cost_map.py , https://github.com/BerriAI/litellm/blob/v1.106.6/litellm/__init__.py

The Ollama chat provider raises its own `OllamaError` from `get_error_class` and LiteLLM maps it by status. Connection refused is therefore expected as `APIConnectionError`, but this was not live-tested; P2.2-05 (opt-in live test) must confirm the three classes. ## Update 2026-11-02 (P2.2)
P2.2 uses a direct Ollama HTTP adapter on httpx (optional extra `rag-foundry-providers[ollama]`, `httpx==0.28.1`) instead of LiteLLM. Reasons:
- User decision 2026-11-02, overriding the Evidence verdict "FITS" for P2.2. Malware shipped in litellm 1.82.7/1.82.8 (GHSA-5mg7-485q-xm76). Every release outside the GHSA-w4c7-34wj-hqm8 range (Enterprise proxy only) is under 2 weeks old, so none meets the pin rule today.
- The wheel is about 36 MB with heavy dependencies.
- LiteLLM cannot tell whether token counts came from Ollama, so `token_source` could not be set honestly.
- LiteLLM does not forward a per-call timeout on the Ollama embedding path.

LiteLLM is re-decided at P2.3/P2.4 planning. The ports are unchanged.
