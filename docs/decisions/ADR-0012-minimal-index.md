# ADR-0012: Minimal chunk and vector index

Date: 2026-11-06
Status: accepted (decided by owner 2026-11-06)

## Context
P3.4 needs a deterministic chunking and dense retrieval baseline over immutable extraction views. The index must preserve source positions, pin the corpus and embedding configuration, enforce project scope during search, and support rebuilding when source, chunking or embedding inputs change. This implements the index lineage and data-isolation requirements in `PROJECT_ARCH.md` sections 6 and 9. The exact built-in plugin API will be validated with C05 and R02 at P3.4 as required by ADR-0002.

## Decision
Decisions D1-D14, all decided by owner 2026-11-06:

- **D1 Layout.** Put Pydantic-only kind types and protocols (`TextBlock`, `ChunkInput`, `ChunkSpan`, `Chunker`, `RetrievedChunk`, `RetrievalResult`, `Retriever`) in `packages/techniques/kinds.py`. Put C05 in the new pure package `packages/chunking`; put `IndexService`, R01 and R02 in the new `packages/indexing`. Although `PROJECT_ARCH.md` lists `packages/retrieval`, P3.4 retrievers only read indexes built by `IndexService` and share its records, so keeping them together avoids churn. Create `packages/retrieval` at P5.1 when lexical/hybrid retrievers arrive and move R01/R02 there with import-path changes only. Built-ins register via `register_builtin_plugins(registry)`; entry points remain for P7.1.
- **D2 Size unit.** Chunk size uses Unicode code points of canonical text, without a tokenizer. Defaults are `chunk_size=800` and `chunk_overlap=100`; size bounds are 32..8000 and overlap is 0..`chunk_size//4`.
- **D3 Splitting.** Try separators in order: `"\n\n"`, `"\n"`, `". "`, `"! "`, `"? "`, U+061F, U+06D4, `"; "`, U+061B, `", "`, U+060C, `" "`, then `""` (hard cut). Keep each separator with its left piece. Hard cuts must not occur before a combining mark, U+200D, U+FE0E/U+FE0F, or inside `\r\n`. Trim edge whitespace and drop whitespace-only chunks. Record `split_level` on every chunk so oversized-paragraph fallback is visible.
- **D4 Coverage and provenance.** Chunks cover the whole canonical text and may cross blocks. Chunk rows store view ID, canonical `start`/`end`, and overlapped `block_ids` in payload order. Compute anchors on demand with `AnchorService.anchors_for_span` (ADR-0011 D1, D12); never store them. Drop and count any chunk overlapping no block as `unanchored_chunk_count`.
- **D5 Text.** Store the chunk text (`canonical[start:end]`) and its SHA-256.
- **D6 Vectors.** Use one untyped pgvector `vector` column on `chunks`; enforce each index version's dimension with a database trigger. Use exact cosine search (`<=>`) and no ANN index in P3.4. Defer HNSW per index version, recall tests and isolation tests until P5. Validate vectors after a float32 round trip because pgvector stores float4: every value must be finite and representable, and norm must be greater than zero. Maximum dimension is 16000.
- **D7 Dependency and migration.** Add no Python dependency. Bind vectors as text `'[x,...]'` with `CAST(:q AS vector)` and read back only distances; do not take the `pgvector` Python package alternative. Migration 0003 is raw SQL only; `sql/models.py` does not mirror the new tables or vector type, and Alembic autogenerate is not used. Migration 0003 runs `CREATE EXTENSION IF NOT EXISTS vector`. Compose and CI use `pgvector/pgvector:0.8.7-pg18-trixie`; downgrade retains the extension.
- **D8 Pinning and lifecycle.** `index_versions` pins chunker ID/version/canonical config JSON and SHA-256; embedding profile ID/provider/model/dimension; distance `cosine`; `embedding_key`; and `corpus_sha256`. The embedding key is SHA-256 over provider, model, dimension, distance and preprocessing using scheme `embedding-key-v1`; profile ID is deliberately excluded. The corpus hash is over sorted `view_id:payload_sha256` lines. States transition only `building -> ready | failed`; otherwise the record is immutable. Search only ready versions. A query embedder must have the same embedding key; equal dimension alone is insufficient. Do not reuse identical builds yet. Recording the Ollama model digest is a known gap.
- **D9 Build location and batching.** `IndexService.build` is worker-side code and never runs in an API request. P3.4 drives it from tests only; the dev CLI comes with the P3.5 CLI and queued job support comes at P8.4. Embed in batches of 32 texts. Any failure marks the version failed; partial builds are never searchable.
- **D10 Embedding port.** Use embeddings only through the `EmbeddingModel` port. The local default is `ollama_embedding_profile()` (bge-m3, 1024 dimensions, zero keys).
- **D11 Retrieval behavior.** R02 performs exact cosine top-k, with default k=5, maximum 50, score `1 - distance`, ties by chunk ordinal, and scope filtering in the same query. An empty result is normal. R01 makes no embedding or database call, returns `grounding="none"`, and has zero hits.
- **D12 Fidelity and catalogue.** C05 is `adaptation` (code points, span-preserving). R02 is `adaptation` (dense retrieval half of RAG with bge-m3; generation is at P3.5). R01 is `faithful`. After P3.4, C05 is `implemented`; R01 and R02 remain `in_progress` until P3.5.
- **D13 Completion evidence.** Offline mechanics use a test-only lexical embedder with its own model name. It is never registered and never presented as a retriever. The roadmap claim that a known fact appears in top-k requires an opt-in live run with Ollama bge-m3 and the compose test database (the model is already pulled, so no download), on a fixture with at least 3*k chunks.
- **D14 Fixture.** Use bilingual Markdown in `tests/indexing/_fixture.py` (escapes): English and Arabic facts, many distractors, and one oversized paragraph.

## Alternatives
- Put R01/R02 in `packages/retrieval` immediately: this duplicates the index records/API boundary while the only P3.4 retrievers read the index `IndexService` builds; defer the package until P5.1.
- Store anchors on chunk rows: anchors are position-derived and should be computed through `AnchorService`, preserving ADR-0011's one-anchor-per-block rule without coupling them to index rows.
- Add the `pgvector` Python package or mirror vector tables in SQLAlchemy models: neither is needed for text-bound vectors and raw SQL migration 0003.
- Add ANN search or reuse an identical prior build in P3.4: defer ANN until P5 and build reuse until there is a demonstrated need.

## Consequences
- Chunking and indexing have explicit typed boundaries while the first built-in strategies can be validated before entry-point discovery is frozen at P7.1.
- Index versions are reproducible and immutable after completion; changes to source bytes, extraction, normalization or chunk boundaries require new index lineage and affected representations/embeddings to be rebuilt. Embedding model/revision/tokenizer/preprocessing/metric changes require a compatible new profile and index; dimension equality is insufficient. Retrieval-setting changes can reuse compatible immutable indexes.
- Exact cosine search favors a simple, inspectable baseline; larger indexes may require the deferred ANN work and its recall and isolation evidence.
- `CREATE EXTENSION vector` requires a database administrator to run it once on managed or production databases before migration, because pgvector is not a trusted extension. The compose and CI database role is a superuser.
- Retrieved chunk text is untrusted data. P3.5 must pass it to the generator as quoted evidence, never as instructions.
- `inspect_chunks` re-reads the payload per chunk; this is accepted for P3.4 (see 05).
- The Ollama model digest is not pinned, and identical builds are not reused.

## Evidence
- ADR-0002 requires validating the exact plugin API with built-in C05 and R02 at P3.4 before freezing v1 at P7.1.
- `PROJECT_ARCH.md` section 6 requires scope-aware isolation and recognizes chunk, embedding profile and index version lineage. Its data-isolation section calls for filters before candidate exposure and scope-aware testing. Section 9's rebuild matrix requires new lineage/rebuilds for source, extraction, normalization and chunk-boundary changes, and a compatible new embedding profile/index for model, revision, tokenizer, preprocessing or metric changes; dimension equality is insufficient. Retrieval setting changes can reuse compatible immutable indexes.
- pgvector README ([github.com/pgvector/pgvector](https://github.com/pgvector/pgvector), read 2026-11-06) and CHANGELOG: latest 0.8.x is 0.8.7 (2026-10-01), the version in the compose image. Elements are single precision (like `real`) and must be finite. A vector can have up to 16,000 dimensions; HNSW and IVFFlat indexes on `vector` support up to 2,000 dimensions. Untyped `vector` columns are allowed; indexes then need an expression cast and a partial index per dimension. `vector_dims()` exists and `<=>` is cosine distance.
- Probe on the compose test database (`pgvector/pgvector:0.8.7-pg18-trixie`; container removed after): `'[1e-05,-1.5E+10,3]'::vector` is accepted (exponent notation works; output rounds to float4: `-1.5000001e+10`). `'[0,0,0]'::vector <=> '[1,2,3]'::vector` returns `NaN`, so zero vectors must be rejected before storage and search. `'[3.5e38]'::vector` raises `"3.5e38" is out of range for type vector`, matching the float32 round-trip check. `vector_dims('[1,2,3]'::vector)` returns 3. `pg_available_extension_versions` reports `trusted = f`, `superuser = t`: pgvector is not trusted and `CREATE EXTENSION vector` needs a superuser. Compose and CI use a superuser; managed/production databases need an administrator to run `CREATE EXTENSION vector` once before migration.
