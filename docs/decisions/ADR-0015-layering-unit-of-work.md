# ADR-0015: Layering, engine lifecycle and Unit of Work

Date: 2026-11-07  
Status: accepted (decided by owner 2026-11-07)

## Context

P3.7 establishes the persistence boundary for the API and worker flows before implementation. It defines database resource lifetimes, transaction ownership, repository behavior and the places where storage may be imported. These decisions preserve short transactions, explicit failure handling and task-safe sessions while keeping model and object-store work outside database transactions.

## Decision

Decisions D1-D15, accepted by owner 2026-11-07:

- **D1 Engine and session lifetimes.** Use one `AsyncEngine` and one `async_sessionmaker` per process: the API lifespan owns them, and CLIs use `open_database`. Open one `AsyncSession` per Unit of Work. Never keep a process-wide session; an `AsyncSession` cannot be shared across concurrent tasks (architecture rule 10). Alternative: create an engine per request.
- **D2 Engine options.** Keep `pool_pre_ping=True`, `hide_parameters=True`, `expire_on_commit=False` and PostgreSQL's default READ COMMITTED isolation. Dispose the engine at lifespan shutdown or CLI exit. Keep the URL as `SecretStr` and never log it. Alternative: change options or isolation as part of this layering change.
- **D3 Layers and imports.** Use web routes for parsing, auth-derived scope, `Depends` and error envelopes; services for business operations, domain ports and transaction boundaries; session-bound repositories in `rag_foundry_storage.sql`; and the database engine and Alembic beneath them. Only `rag_foundry_api.container` and worker CLIs import `rag_foundry_storage`; only the storage package imports SQLAlchemy. `tests/repo/test_layering.py` enforces this. Alternative: let services or routes import storage or SQLAlchemy directly.
- **D4 Domain ports.** Define `UnitOfWork` and `UnitOfWorkFactory` in `rag_foundry_domain.uow`. A Unit of Work is an async context manager exposing `documents`, `extractions`, `indexes`, `prompts`, `settings`, `commit()`, `rollback()` and `read_only`. Its factory is called as `__call__(*, read_only=False)`. Exiting without commit rolls back. In read-only mode, `commit()` and every repository write method raise `RuntimeError`. Defer database-level `SET TRANSACTION READ ONLY`, since it eagerly acquires a connection and changes where `store_unavailable` is raised. A Unit of Work belongs to its opening task; use from another task raises `RuntimeError`. Nesting is unsupported. Alternative: allow implicit commits, cross-task use or nested Units of Work.
- **D5 Transaction ownership.** Services own transaction boundaries. A service method opens short Units of Work and explicitly commits before returning; dependency teardown never commits. In FastAPI 0.162, a yield dependency with default `scope="request"` exits after the response is sent, so a teardown commit failure can follow a 2xx. `Depends(..., scope="function")` exits before the response (available since 0.121.0), but a request-scoped dependency cannot depend on a function-scoped sub-dependency; exceptions reach the dependency at `yield` and must be re-raised. Uploads and runs would also hold transactions through streaming or model calls. Alternative: commit a request-scoped Unit of Work in `scope="function"` teardown. Sources: [yield dependencies](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/) and [advanced dependencies](https://fastapi.tiangolo.com/advanced/advanced-dependencies/).
- **D6 Flow boundaries.** Preserve current commit points. Intake uses a read Unit of Work, streams to object storage with no Unit of Work open, then uses a write Unit of Work. Extraction reads, does work, then writes. Index build reads view rows, reads payloads with no Unit of Work, writes index creation, embeds each batch with no Unit of Work, writes `add_chunks`, then writes `mark_ready`; after failure and exit of the failing Unit of Work, a fresh write Unit of Work calls `mark_failed`. Runs use one short read-only transaction before model calls for index version, settings overrides and active prompts. Under READ COMMITTED each statement sees the latest committed data, reducing round trips compared with today but not providing a snapshot. Search and anchor reads use short read Units of Work after embedding. No Unit of Work remains open during model calls or object-store I/O. Runs write nothing (P8.4). Dev scope upsert uses one write Unit of Work in the lifespan. Alternative: use REPEATABLE READ for run reads, which provides a snapshot but eagerly acquires a connection.
- **D7 Repository behavior.** Repositories receive an `AsyncSession`; they never commit, roll back or close it. Each write method runs in one `session.begin_nested()` savepoint, so a mapped error undoes only that method's work and leaves the Unit of Work usable. Keep tenant filters, UUID checks, `NotFoundError`, IntegrityError and OperationalError/InterfaceError mapping, FOR UPDATE and advisory transaction locks unchanged. Assume advisory transaction locks remain held until the Unit of Work ends even after savepoint rollback; PostgreSQL documents release behavior for table and row locks, not advisory transaction locks. Keep write Units of Work to one business step. A Unit of Work taking multiple advisory locks acquires them by ascending lock-key text (`doc:` < `sha:` < `view:`) and must have a deadlock test. Use Core statements only. The Unit of Work does not touch the connection in `__aenter__`. Alternative: repository-owned transactions, multiple unbounded business steps per write Unit of Work, or ORM statements.
- **D8 Persistence failures.** At commit, map `OperationalError` and `InterfaceError` to `StoreError("store_unavailable")`, returned by the API as 503 `storage_unavailable` with fixed text `storage unavailable`. Map other commit-time `DBAPIError` to `StoreError("commit_failed")`, returned as 500 `storage_error` with fixed text `storage error`. If a backend is killed mid-Unit of Work, prompt/settings reads and writes retain their `store_unavailable` codes; document, extraction and index methods retain today's behavior and let the driver error propagate to the generic 500. Savepoint rollback, Unit of Work rollback and close failures never mask the original error. Never expose database text. A connection lost exactly at commit of a prompt/settings write now raises `StoreError`; no route writes those yet. Alternative: expose database messages or let cleanup failures replace the triggering error.
- **D9 Per-call adapter.** Provide `rag_foundry_domain.uow_adapters.PerCall`, which implements existing ports through one Unit of Work per method call and commits writes. Use it for shared check suites and transitional wiring. At the end, production uses it only for index reads during run retrieval. Alternative: migrate every caller at once or retain it as general production wiring.
- **D10 In-memory test factory.** Provide `rag_foundry_domain.uow_testing.InMemoryUnitOfWorkFactory`. Serialize write Units of Work, snapshot and restore on rollback, and reject writes in read-only Units of Work. It makes no isolation claim. Alternative: imply database isolation in the test double.
- **D11 FastAPI integration.** Keep `create_app(settings=None)` only; validate the runtime settings file with unchanged startup failure timing. The lifespan enters `container.open_container(settings, runtime)`, which opens the Database, upserts the dev scope in dev/test, builds `AppContainer` and disposes on exit, then yields `{"container": ...}`. Providers in `rag_foundry_api/deps.py` return `X | None`; routes retain their current 503 checks and therefore their current 404/422/503 ordering. Tests use `app.dependency_overrides`; the lifespan runs only inside `with TestClient(app)`. Keep `LocalRunner` and the prompt cache as app singletons. Alternative: construct storage at import time, move route checks, or construct app resources outside the lifespan. Source: [FastAPI testing events](https://fastapi.tiangolo.com/advanced/testing-events/).
- **D12 Worker database helpers.** Put `open_database(url)` and `run_db_main(coro)` in `rag_foundry_storage.sql.database` and share them across CLIs. `run_db_main` uses a Selector loop on Windows. Alternative: duplicate database lifecycle code in each CLI.
- **D13 Alembic.** Keep Alembic separate and unchanged: `env.py` owns a NullPool async engine; `run_migrations` is synchronous and called outside any running event loop. The API never migrates. Alternative: migrate during API startup or invoke synchronous migrations on an active event loop.
- **D14 Proof.** Require the P3.7-00 tests to pass before and after, the full check, and `pytest -m db` on a fresh test database. Include atomicity, savepoint, read-only-write, task-guard, killed-backend and no-Unit-of-Work-during-model-calls-or-object-store-I/O tests; keep golden requests unchanged. Run one live answer and obtain owner approval at run time. Alternative: three live runs as in P3.6.
- **D15 Evidence.** The FastAPI dependency lifecycle and testing details, SQLAlchemy async-session and transaction behavior, and PostgreSQL lock behavior described above were checked by the orchestrator on 2026-11-06 against [FastAPI yield dependencies](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/), [FastAPI advanced dependencies](https://fastapi.tiangolo.com/advanced/advanced-dependencies/), [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/21/orm/extensions/asyncio.html), [SQLAlchemy session transactions](https://docs.sqlalchemy.org/en/21/orm/session_transaction.html), and [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html). Alternative: leave these lifecycle and lock assumptions undocumented.

## Alternatives

- Create an engine per request or let a process-wide session serve concurrent work; retain process-scoped engines and task-scoped sessions.
- Put transaction ownership in web dependency teardown or repositories; retain explicit service-owned commits and session-bound repositories.
- Keep Units of Work open through model calls, object-store I/O or streaming; retain short transactions around database operations.
- Use implicit commit, nested/cross-task Units of Work, or a test double claiming isolation; retain explicit commit, task ownership and documented test-double limits.
- Let API startup migrate the database or allow database imports across layers; keep Alembic separate and enforce the storage boundary.

## Consequences

- Each task gets an independent session and services make commit points visible in their business flow.
- Database transactions do not span external I/O, model calls or upload streaming.
- Repository savepoints preserve Unit of Work usability after a mapped method failure; advisory-lock ordering and single-step writes constrain deadlocks.
- API and worker lifecycle code share the database boundary, while routes preserve existing availability checks and status ordering.
- Commit and backend failures have fixed public messages and preserve the original exception during cleanup.
- The in-memory implementation supports rollback-oriented tests without claiming database isolation; database-specific guarantees require the fresh-database checks in D14.
