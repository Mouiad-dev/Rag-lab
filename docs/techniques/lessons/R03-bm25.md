# R03: BM25 lexical search

## Intuition

BM25 ranks chunks by query-term overlap, giving more weight to rarer terms and moderating the effect of repeated terms and document length. It is a lexical retriever over a ready index version.

## Mechanism

`BM25Retriever` lives in `packages/indexing/src/rag_foundry_indexing/bm25.py`. It uses Okapi BM25 with `k1=1.2`, `b=0.75` by default and Lucene-style IDF:

`log(1 + (N - df + 0.5) / (df + 0.5))`.

The `lab-lexical-v1` tokenizer normalizes Arabic with the shared multilingual normalizer, folds Arabic-Indic digits, casefolds, emits word tokens, then adds a whole identifier token for identifiers containing digits. Thus `AB-1234` produces `ab`, `1234`, and `ab-1234`. Harakat, tatweel, alef forms and bidi controls are normalized; the tokenizer does not stem words or remove clitics.

Corpus statistics are built in-process when a retriever first runs and cached on that retriever instance. They are rebuilt for a new retriever, are not stored in the index, and are bounded by `max_chunks` (default 20,000). Retrieval checks that the index version is ready; it does not build an index itself.

## Worked example

This in-memory example uses the `FakeIndex` shape from `tests/indexing/test_bm25.py`. The first chunk is the exact identifier match; the alternatives have a different identifier or a spaced form.

## Runnable demo

```powershell
$env:PYTHONIOENCODING='utf-8'; uv run python -c "import asyncio; from types import SimpleNamespace; from rag_foundry_domain.indexing import IndexState; from rag_foundry_domain.testing import make_scope; from rag_foundry_indexing import BM25Config, BM25Retriever; texts=['\u0631\u0642\u0645 \u0627\u0644\u0642\u0637\u0639\u0629 AB-1234','\u0631\u0642\u0645 \u0627\u0644\u0642\u0637\u0639\u0629 AB-1243','\u0631\u0642\u0645 \u0627\u0644\u0642\u0637\u0639\u0629 AB 1234']; chunks=[SimpleNamespace(id=f'c{i}', extraction_view_id='v', start=0, end=len(t), block_ids=('b',), text=t, ordinal=i) for i,t in enumerate(texts)]; index=type('FakeIndex',(),{'state':IndexState.READY,'get_index_version':lambda self,s,v: asyncio.sleep(0,result=SimpleNamespace(state=self.state)),'list_chunks':lambda self,s,v,offset=0,limit=100: asyncio.sleep(0,result=chunks[offset:offset+limit])})(); r=BM25Retriever(BM25Config(),scope=make_scope(),index_version=SimpleNamespace(id='version'),index=index); result=asyncio.run(r.retrieve('AB-1234')); [print('rank',h.rank,'score',round(h.score,4),'components',[(c.name,c.term,round(c.value,4)) for c in h.score_components],'text',ascii(h.text)) for h in result.hits]; lost=asyncio.run(r.retrieve('\u0645\u0643\u062a\u0628\u0629')); print('losing query hits:',len(lost.hits))"
```

## Failure case

The query `\u0645\u0643\u062a\u0628\u0629` (maktaba, “library”) does not retrieve `\u0627\u0644\u0645\u0643\u062a\u0628\u0629` (“the library”): BM25 has no stemming or clitic removal. This losing case is run in the demo.

## Limitations

This is in-process lexical scoring, not a persisted inverted index. Each retriever builds corpus statistics from chunks, so memory and startup work grow with the indexed corpus up to `max_chunks`. It needs an already-ready index version. Token normalization does not make Arabic roots or clitics equivalent.

## Baseline comparison

The real testdb comparison and PostgreSQL behavior are recorded in [lexical observations](../../evidence/P5.1/lexical_observations.md). For `AB-1234`, R03 ranked the matching Arabic part-number line first at `8.4872`, with `bm25_term` contributions `ab 3.4316`, `1234 2.5278`, and `ab-1234 2.5278`. The evidence explicitly notes that the scores use different formulas and are not comparable.
