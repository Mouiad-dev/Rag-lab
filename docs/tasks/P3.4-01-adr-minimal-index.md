  - D1 Layout: kind types/protocols (`TextBlock`, `ChunkInput`, `ChunkSpan`, `Chunker`, `RetrievedChunk`, `RetrievalResult`, `Retriever`) in `packages/techniques/kinds.py` (pydantic only). C05 in new pure package `packages/chunking`; `IndexService`, R01, R02 in new package `packages/indexing`. Why not `packages/retrieval` yet (SUMMARY lists it separately): P3.4 retrievers only read indexes that `IndexService` builds and share its records; one member is less churn. `packages/retrieval` is created at P5.1 when lexical/hybrid retrievers arrive, and R01/R02 move there (import path change only). Built-ins register via `register_builtin_plugins(registry)`; entry points stay for P7.1.
  - D2 Size unit: Unicode code points of canonical text (no tokenizer). Defaults `chunk_size=800`, `chunk_overlap=100`; bounds 32..8000, overlap 0..chunk_size//4.
  - D3 Separators in order: `"\n\n"`, `"\n"`, `". "`, `"! "`, `"? "`, U+061F, U+06D4, `"; "`, U+061B, `", "`, U+060C, `" "`, `""` (hard cut). Separator stays with the left piece. Hard cuts never land before a combining mark, U+200D, U+FE0E/U+FE0F, or inside `\r\n`. Edge whitespace trimmed; whitespace-only chunks dropped. Each chunk records `split_level` so fallback on an oversized paragraph is visible.
  - D4 Chunks cover the whole canonical text and may cross blocks. Chunk rows store view id, canonical `start`/`end`, overlapped `block_ids` (payload order); anchors are computed on demand with `AnchorService.anchors_for_span` (ADR-0011 D1, D12), never stored. A chunk overlapping no block is dropped and counted (`unanchored_chunk_count`).
  - D5 Chunk text is stored (copy of `canonical[start:end]`) with its SHA-256.
  - D6 Vectors: one untyped pgvector `vector` column on `chunks`; per-index dimension enforced by a DB trigger; exact cosine search (`<=>`), no ANN index in P3.4 (HNSW per index version, with recall and isolation tests, deferred to P5). Vectors are validated after a float32 round trip (pgvector stores float4): every value finite and representable, norm > 0. Max dim 16000.
  - D7 No new Python dependency: vectors bound as text `'[x,...]'` with `CAST(:q AS vector)`; only distances read back. (Alternative not taken: `pgvector` Python package.) Migration 0003 is raw SQL only; `sql/models.py` does not mirror the new tables (no vector type there); do not use Alembic autogenerate. It runs `CREATE EXTENSION IF NOT EXISTS vector` (compose and CI use `pgvector/pgvector:0.8.7-pg18-trixie`); downgrade keeps the extension.
  - D8 Pinning: `index_versions` pins chunker id/version/canonical config JSON + SHA-256, embedding profile id/provider/model/dim, distance `cosine`, `embedding_key` (SHA-256 of provider, model, dim, distance, preprocessing; scheme `embedding-key-v1`; profile id deliberately not part of it), `corpus_sha256` over sorted `view_id:payload_sha256` lines. States `building -> ready | failed` only; otherwise immutable; search only on `ready`. A query embedder must have the same `embedding_key` (equal dimension is not enough). No reuse of identical builds yet. Ollama model digest not recorded (known gap).
  - D9 Where: `IndexService.build` is worker-side code (never in an API request). P3.4 drives it from tests only; the dev CLI comes with the P3.5 CLI, the queued job at P8.4. Batches of 32 texts; any failure marks the version `failed`; nothing partial is searchable.
  - D10 Embeddings only through the `EmbeddingModel` port; the local default is `ollama_embedding_profile()` (bge-m3, 1024 dims, zero keys).
  - D11 R02: exact cosine top-k, default k 5, max 50, score = 1 - distance, ties by chunk ordinal, scope filter in the same query; empty result is a normal outcome. R01: no embedding or DB call, `grounding="none"`, zero hits.
  - D12 Fidelity: C05 `adaptation` (code points, span-preserving), R02 `adaptation` (dense retrieval half of RAG with bge-m3; generation at P3.5), R01 `faithful`. Catalogue after P3.4: C05 `implemented`; R01, R02 `in_progress` until P3.5.

## Evidence gathered by the orchestrator (2026-11-06)
Copy these into ADR-0012 "Evidence".
- pgvector README (github.com/pgvector/pgvector, read 2026-11-06) and CHANGELOG: latest 0.8.x is 0.8.7 (2026-10-01), the version in the compose image; elements are single-precision (like `real`) and must be finite; up to 16,000 dimensions per vector, HNSW and IVFFlat index up to 2,000 dimensions for `vector`; an untyped `vector` column is allowed (indexes then need an expression cast plus a partial index per dimension); `vector_dims(vector)` exists; `<=>` is cosine distance.
- Probe on the compose testdb (`pgvector/pgvector:0.8.7-pg18-trixie`), container removed after:
  - `'[1e-05,-1.5E+10,3]'::vector` is accepted (exponent notation works; output rounds to float4: `-1.5000001e+10`).
  - `'[0,0,0]'::vector <=> '[1,2,3]'::vector` returns `NaN` (zero vectors must be rejected before storage and before search).
  - `'[3.5e38]'::vector` raises `"3.5e38" is out of range for type vector` (float4 overflow; matches the float32 round-trip check).
  - `vector_dims('[1,2,3]'::vector)` returns 3.
  - `pg_available_extension_versions`: `trusted = f`, `superuser = t`. pgvector is NOT a trusted extension: `CREATE EXTENSION vector` needs a superuser. The compose and CI database user is a superuser, so migration 0003 works there; a managed or production database needs an administrator to run `CREATE EXTENSION vector` once before migrating (record as a known operational requirement).
