## Goal
The compose stack stores uploads on a named volume, runs migrations before api/worker start, and offers a throwaway `testdb` under profile `test`. CI runs the `db`-marked tests against Postgres in a separate ubuntu job. Existing `.env` files keep working.

## Change
- `Dockerfile`: create `/data/objects` owned by `10001:10001` (the existing non-root app user) so the named volume inherits that owner.
- `compose.yaml`:
  - volume `objects` at `/data/objects` on api (rw) and worker (`:ro`); `RAG_FOUNDRY_OBJECT_STORE_ROOT=/data/objects` on both.
  - `RAG_FOUNDRY_DATABASE_URL: postgresql+psycopg://${POSTGRES_USER:-rag_foundry}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB:-rag_foundry}` on api, worker and `migrate` (note in `.env.example`: the password must be URL-safe).
  - one-shot `migrate` service (same image, `command: ["rag-foundry-migrate"]`, same hardening as api), depends on `db` healthy; api and worker depend on it with `service_completed_successfully`.
  - Spool cap (decision): api `tmpfs` becomes `/tmp:size=512m`. Starlette spools multipart file parts to `/tmp`; 512 MiB fits several 100 MiB uploads. A full tmpfs surfaces as a 500 envelope, never a host-disk fill. Staged objects go to the volume, not `/tmp`.
  - service `testdb` under `profiles: [test]` only: `pgvector/pgvector:0.8.7-pg18-trixie`, data on `tmpfs`, port `127.0.0.1:55432:5432`, `POSTGRES_USER: rag_foundry`, `POSTGRES_DB: rag_foundry`, `POSTGRES_PASSWORD: ${POSTGRES_TEST_PASSWORD:-}` (user/db match the `.env.example` URL `postgresql+psycopg://rag_foundry:<placeholder>@127.0.0.1:55432/rag_foundry`), healthcheck like `db`. Uses the **non-failing** `:-` form so plain `docker compose up` with an old `.env` still works; the postgres image itself refuses to start `testdb` with an empty password, which is the intended failure.
- `.env.example`: placeholder `POSTGRES_TEST_PASSWORD=` and a commented `RAGF_TEST_DATABASE_URL=postgresql+psycopg://rag_foundry:<password>@127.0.0.1:55432/rag_foundry`.
- `ci.yml`: new job `db-tests` (ubuntu-latest only; same pinned checkout/setup-uv SHAs and `contents: read`) with `services: postgres` on the same pgvector image, `POSTGRES_PASSWORD: ragf-ci-throwaway` (comment: fixed literal for a throwaway CI container, not a secret), health options, port 5432; env `RAGF_TEST_DATABASE_URL=postgresql+psycopg://postgres:ragf-ci-throwaway@localhost:5432/postgres`; steps `uv sync --locked`, `uv run pytest -m db -v`. Do not change the `check` matrix job or the `image` job's steps; in the Result, note whether the runner's compose accepts the one-shot `migrate` service (exits 0) under `up --wait`.
- CONTRIBUTING: 4 lines: start `testdb` with `--profile test`, export `RAGF_TEST_DATABASE_URL`, run `uv run pytest -m db`, stop it with `docker compose --profile test rm -sf testdb` (data gone; dev stack untouched).
