## Change
- Create `docs/decisions/ADR-0015-layering-unit-of-work.md` (Context / Decision / Alternatives / Consequences / Evidence). Each D gives the default and the alternative:
  - D1 Lifetimes: one `AsyncEngine` + one `async_sessionmaker` per process (API lifespan; CLIs `open_database`); one `AsyncSession` per Unit of Work; never a process-wide session (AsyncSession is not safe across concurrent tasks; rule 10). Alt: engine per request (rejected).
  - D2 Engine options unchanged: `pool_pre_ping=True`, `hide_parameters=True`, `expire_on_commit=False`, PostgreSQL default READ COMMITTED; disposed on lifespan shutdown / CLI exit; URL stays `SecretStr`, never logged.
  - D3 Layers: web (routes: parse, scope from auth, `Depends`, error envelopes) -> services (business operations, own transaction boundaries, domain ports only) -> UoW + repositories (`rag_foundry_storage.sql`, session-bound) -> DB (engine, Alembic). Only `rag_foundry_api.container` and worker CLIs import `rag_foundry_storage`; no package except storage imports `sqlalchemy`. Enforced by `tests/repo/test_layering.py`.
  - D4 Domain port `rag_foundry_domain.uow`: `UnitOfWork` (async context manager; `documents`, `extractions`, `indexes`, `prompts`, `settings`; `commit()`, `rollback()`, `read_only`) and `UnitOfWorkFactory.__call__(*, read_only=False)`. Exit without commit rolls back. Read-only: `commit()` and every repository write method raise `RuntimeError`; DB-level `SET TRANSACTION READ ONLY` deferred (it acquires the connection eagerly and moves where `store_unavailable` is raised). A UoW belongs to the task that opened it (other task -> `RuntimeError`); no nesting.
  - D5 Transaction boundaries belong to services: a service method opens short UoWs and commits explicitly before returning; no commit in dependency teardown. Verified 2026-11-06: in FastAPI 0.162 a yield dependency's default `scope="request"` exits after the response is sent, so a teardown commit failure would follow a 2xx; `Depends(..., scope="function")` (since 0.121.0) exits before the response, but a request-scoped dependency cannot have a function-scoped sub-dependency; exceptions reach the dependency at `yield` and must be re-raised. Uploads and runs would also hold a transaction through streaming or model calls. Alt: request-scoped UoW with `scope="function"` committing in teardown. Sources: https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/ , https://fastapi.tiangolo.com/advanced/advanced-dependencies/
  - D6 Per flow (same commit points as today): intake read UoW -> stream/object store (no UoW) -> write UoW; extraction read -> work -> write UoW; index build read view rows -> payload reads (no UoW) -> write create -> per batch embed (no UoW) then write `add_chunks` -> write `mark_ready`; on failure, after the failing UoW has exited, a fresh write UoW `mark_failed`; runs: one short read-only transaction before any model call (index version, settings overrides, active prompts; READ COMMITTED, so each statement sees the latest committed data: fewer round trips than today, not a snapshot); search and anchor reads in short read UoWs after the embed call. No UoW open during model calls or object-store I/O. Runs write nothing (P8.4). Dev scope upsert: one write UoW in the lifespan. Alt: REPEATABLE READ for the run read UoW (a real snapshot; eager connection).
  - D7 Repositories take an `AsyncSession`; never commit, roll back or close. Every write method body runs in one savepoint (`session.begin_nested()`): a mapped error undoes only that method's work and the UoW stays usable. Tenant filters, UUID checks, `NotFoundError`, IntegrityError and OperationalError/InterfaceError mapping, FOR UPDATE and advisory xact locks unchanged. Locks: assume advisory xact locks are held until the UoW ends even after a savepoint rollback (PostgreSQL documents release for table/row locks, not advisory xact locks); write UoWs stay one business step. Ordering rule: a UoW taking more than one advisory lock acquires them in ascending lock-key text order (`doc:` < `sha:` < `view:`) and must add a deadlock test. Core statements only. The UoW never touches the connection in `__aenter__`.
  - D8 Failures: commit `OperationalError`/`InterfaceError` -> new `StoreError("store_unavailable")` (API 503 `storage_unavailable` "storage unavailable"); other `DBAPIError` at commit -> `StoreError("commit_failed")` (500 `storage_error` "storage error"). A backend killed mid-UoW: prompt/settings reads and writes keep their `store_unavailable` codes; document/extraction/index methods keep today's behaviour (the driver error propagates unmapped to the generic 500); errors from savepoint rollback, rollback or close never mask the original. Fixed messages, never DB text. Stated change: a connection lost exactly at commit of a prompt/settings write now raises `StoreError` (no route writes those yet).
  - D9 `rag_foundry_domain.uow_adapters.PerCall`: one UoW per method call (writes commit), implements the existing ports; used by the shared check suites and as transitional wiring; at the end production uses it only for `indexes` reads during retrieval in runs.
  - D10 `rag_foundry_domain.uow_testing.InMemoryUnitOfWorkFactory`: test double; write UoWs serialized, snapshot/restore on rollback, read-only UoWs reject writes; claims no isolation.
  - D11 FastAPI: `create_app(settings=None)` only; it validates the runtime settings file (startup failure timing unchanged). The lifespan enters `container.open_container(settings, runtime)` (opens the Database, upserts the dev scope in dev/test, builds `AppContainer`, disposes on exit) and yields `{"container": ...}`. Providers in `rag_foundry_api/deps.py` return `X | None`; routes keep their 503 checks where they are today, so status order (404/422/503) is unchanged. Tests use `app.dependency_overrides`; the lifespan runs only under `with TestClient(app)` (https://fastapi.tiangolo.com/advanced/testing-events/). `LocalRunner` and the prompt cache stay app singletons.
  - D12 Workers: `open_database(url)` and `run_db_main(coro)` (Selector loop on Windows) in `rag_foundry_storage.sql.database`, shared by all CLIs.
  - D13 Alembic unchanged and separate: `env.py` owns a NullPool async engine, `run_migrations` is sync and called outside any loop; the API never migrates.
  - D14 Proof: 00 tests pass before and after; full check; `pytest -m db` on a fresh testdb; atomicity, savepoint, read-only-write, task-guard, killed-backend and "no UoW during model calls or object-store I/O" tests; golden requests unchanged; 1 live answer run (owner OK at run time; alt: 3 runs as in P3.6).

Write them in Evidence with that date.
