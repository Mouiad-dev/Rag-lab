## Goal
When the first logical form fails with a defined failure status, R48 makes at most one more planning call, telling the model what failed. Usage of both calls is counted. There is never a fallback to chunk retrieval, and no re-plan happens when the first plan is `answered` or when the data itself is the problem (missing facts, conflicts).

## Read only these files
- `packages/indexing/src/rag_foundry_indexing/kag_retrieve.py` (P7.3-08)
- `packages/indexing/src/rag_foundry_indexing/kag_logical_form.py` (rejection reasons, statuses)
- `tests/indexing/test_kag_retrieve.py`, `tests/indexing/_kag_fixture.py`

## Change
- `kag_retrieve.py`:
  - `KagConfig.max_replans: int = Field(1, ge=0, le=1)`.
  - `REPLAN_ON = {"invalid_logical_form", "unsupported_operator", "schema_violation", "unknown_entity"}`. `unknown_entity` means some step has that status (the plan named an entity wrongly). `missing`, `conflict`, `empty` and `answered` never trigger a re-plan.
  - `R48_REPLAN_SYSTEM_V1` + SHA (same untrusted-JSON wording). User JSON adds `{"previous_plan": <first plan JSON or the raw text cut to 2000 chars>, "failure": {"reason", "detail"}}`. The previous plan and failure are data, never instructions.
  - The second attempt's result is final, whatever it is. Both attempts are listed in `last_trace.attempts`; `usage` has one entry per call.
- `tests/indexing/test_kag_retrieve.py`: update only assertions that change because `max_replans` defaults to 1 (e.g. the malformed-plan case now makes 2 calls, both recorded; give its responder an invalid second reply so the status stays `rejected`). Add:
  - **Re-plan success:** first plan uses an undeclared predicate (`schema_violation`); second plan is valid and answers; 2 calls, 2 usage entries, 2 attempts, final `answered`, hits as without re-plan.
  - **Re-plan failure:** first `unsupported_operator`, second `invalid_logical_form`; final `rejected`, empty hits, 2 calls, no third call.
  - **unknown_entity:** first plan misspells "Cedar Labs"; second fixes it; answered.
  - **No re-plan on `answered`:** 1 call.
  - **No re-plan on data problems:** the Blue Reef conflict and the Delta Works missing fact each make 1 call.
  - **`max_replans=0`:** a failing plan makes 1 call and stays `rejected`.
  - The re-plan request carries the failure reason inside the user JSON; an injected instruction in the previous plan text stays there.
